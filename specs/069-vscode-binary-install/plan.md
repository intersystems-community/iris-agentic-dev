# Implementation Plan: VS Code Extension Auto-Installs Binary

**Branch**: `069-vscode-binary-install` | **Date**: 2026-07-24 | **Spec**: [spec.md](spec.md)

## Summary

Add a managed-download tier to the existing VS Code extension so the binary is
auto-installed on first activation. The extension already handles the `serverPath`
setting and PATH lookup; this plan adds a third tier that downloads the correct
platform binary from GitHub Releases, caches it in `globalStorageUri`, and
re-downloads when the cached version differs from the extension version.
All changes are in `vscode-iris-agentic-dev/`. No new Rust code, no new npm
runtime dependencies.

## Technical Context

**Language/Version**: TypeScript 5, Node.js (VS Code extension host runtime)
**Primary Dependencies**: VS Code API (`vscode`), Node built-ins (`https`, `fs`,
`stream/promises`, `path`, `os`). `which` already present for PATH lookup.
**Storage**: Two files in `context.globalStorageUri` (VersionMarker + ManagedBinary)
**Testing**: Node `--test` runner (already used by `test/redact.test.cjs`)
**Target Platform**: VS Code 1.99+ on Windows x64, macOS arm64/x86_64, Linux x86_64
**Performance Goals**: Download ≤ 8 MB binary; progress visible within 500 ms
**Constraints**: Zero new runtime npm deps; activation must complete or show error
within the binary download time (~5–30 s depending on network)

## Phases

### Phase 1 — Platform & URL helpers (pure functions, easiest to test)

New file `platform.ts`:

- `getBinaryName(platform: string, arch: string): string | null` — maps
  `process.platform` + `process.arch` to `iris-agentic-dev-{PLATFORM}-{ARCH}[.exe]`.
  Returns `null` for unsupported combinations (Linux arm64, etc.).
- `getDownloadUrl(version: string, platform: string, arch: string): string | null` —
  returns full GitHub Releases URL or `null` for unsupported platforms.

Tests (`platform.test.cjs`): all four supported combinations + unsupported cases.
Write tests first.

### Phase 2 — Download helper

New file `download.ts`:

- `downloadBinary(url: string, dest: string, onProgress: (fraction: number) => void): Promise<void>`
  - Follows up to 10 redirects (GitHub returns 302 → S3 presigned URL)
  - Streams to `dest + '.tmp'`, renames atomically on completion
  - Throws on HTTP error status, network error, or incomplete transfer

No unit test for the actual HTTP call (requires network). Integration test covered
by manual smoke test in quickstart.md. The function is thin enough to test by
inspection.

### Phase 3 — Managed install logic

New file `managedInstall.ts`:

- `resolveServerBinary(context: vscode.ExtensionContext): Promise<string | null>`

Resolution order:

1. `iris-agentic-dev.serverPath` setting — return if set and executable
2. `which.sync('iris-agentic-dev')` PATH lookup — return if found
3. Managed download:
   a. Determine `binaryName` from platform — return `null` if unsupported
   b. Read `globalStorageUri/iris-agentic-dev.version` — compare to `packageJSON.version`
   c. If match and binary exists → return cached path (cache hit)
   d. If mismatch or absent → download with progress notification
   e. On download success: `chmod 0o755` (mac/linux), write version marker → return path
   f. On download failure with stale cache → log warning, return stale binary path
   g. On download failure with no cache → log error, return `null`
   h. Windows: rename existing binary to `iris-agentic-dev-old.exe` before writing new one;
   attempt to delete old on next cache-hit activation

**Concurrency guard**: module-level `let activeResolve: Promise<string | null> | undefined`
— prevents duplicate downloads when multiple windows activate simultaneously.

Tests (`managedInstall.test.cjs`): version match → no download; version mismatch →
download triggered; download failure + stale cache → stale path returned; download
failure + no cache → null returned; serverPath setting respected; PATH binary respected.
Write tests first (mock `downloadBinary` and `fs` operations).

### Phase 4 — Wire into extension.ts

Modify `extension.ts`:

- Remove `findIrisDev()` function
- Import `resolveServerBinary` from `managedInstall.ts`
- Change `activate()` to `async`
- Await `resolveServerBinary(context)` before constructing `IrisDevMcpProvider`
- Pass the resolved binary path into `IrisDevMcpProvider` (or store on context);
  `provideMcpServerDefinitions` uses the already-resolved path rather than calling
  `findIrisDev()` again on each config change
- On `null` return from `resolveServerBinary`: show the existing error message (already
  written at lines 103-110) and register an empty provider

### Phase 5 — Package and test

- Update `package.json` `test` script to run all three test files
- Manual smoke test on macOS (clean cache, confirm download + start)
- Update `README.md` in `vscode-iris-agentic-dev/` to remove "binary must be on PATH"
  requirement; note auto-install behavior
- Bump extension version in `package.json` to stay in sync with binary version at
  release time (deferred to release, not a code task)

## Quickstart (manual smoke test)

```bash
# 1. Build extension
cd vscode-iris-agentic-dev
npm run compile

# 2. Clear managed cache to force download
rm -rf "$HOME/Library/Application Support/Code/User/globalStorage/intersystems-community.vscode-iris-agentic-dev"

# 3. Open VS Code with the extension loaded (F5 in Extension Development Host)
#    Activate the extension — watch for the progress notification
#    Confirm the binary appears in globalStorage

# 4. Reactivate — confirm no second download (cache hit)

# 5. Corrupt the version marker — confirm re-download
echo "0.0.0" > "$HOME/Library/Application Support/Code/User/globalStorage/intersystems-community.vscode-iris-agentic-dev/iris-agentic-dev.version"
# Reactivate — confirm fresh download

# 6. Run automated tests
npm test
```

## Open Questions / Deferred

- **Extension version pinning at release**: the extension `package.json` version must
  match the binary version tag. Release checklist item, not a code task.
- **Linux arm64**: out of scope. Return `null` from `getBinaryName` for that combination;
  existing PATH/setting tiers still work for users who build from source.
- **Marketplace VSIX**: publishing the updated extension requires the Azure DevOps PAT
  (blocked on code signing approval per project memory). Binary auto-install ships in
  the VSIX but Marketplace publish is a separate step.
